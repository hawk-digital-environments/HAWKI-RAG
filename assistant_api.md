# Assistant API Contract

## Purpose

This document defines step 1 of the assistant-facing Laravel API for the current `v1.5` RAWKI backend.

The goal is to let an external assistant system talk only to Laravel in order to:

- add a file-backed document
- ingest that file into Qdrant
- optionally ingest graph data into Neo4j
- delete the indexed document from Qdrant and Neo4j
- update the indexed document only when the incoming file is newer

This is a contract and implementation plan for the Laravel API surface. It is not the final Swagger file yet.

## Current Backend Reality

The current branch already has most of the execution pieces, but they are split across Laravel and the Python bridge:

- Laravel accepts single-file uploads and starts one Temporal ingest workflow per uploaded file.
- Python Temporal converts and ingests the file contents.
- Python bridge already exposes:
  - `POST /ingest`
  - `DELETE /documents/{doc_id}`
  - `PUT /documents/{doc_id}`
- PostgreSQL already stores Laravel-owned metadata for:
  - `datasets`
  - `documents`
  - `pipeline_tasks`
  - `pipeline_jobs`
  - `ingestion_sources`
  - `ingested_pages`

Important constraints from the current codebase:

- The existing upload route is single-file, not bulk multi-file.
- One uploaded file becomes one Temporal `source_id` and one workflow execution.
- One uploaded file may expand into one or more bridge-level documents after conversion.
- One bridge-level document may expand into many Qdrant chunks.
- The current Laravel `documents` table is an ingestion artifact table, not yet a stable assistant-facing public resource.

## Core Design Decision

The assistant API must treat one uploaded file as one logical public resource even if the ingest pipeline expands that file into:

- multiple bridge-level `doc_id` values
- multiple Qdrant chunks per bridge document
- multiple Neo4j entities and relationships

Because of that, the assistant API needs its own stable public document identity in PostgreSQL.

The assistant system must not manage chunks directly.

## Public Resource Model

The assistant-facing resource is called an `assistant document`.

An assistant document represents one logical file lifecycle:

- the uploaded file
- its newest source timestamp
- the active indexed outputs derived from it
- the current index status

It is not the same thing as:

- the current Laravel `documents.id`
- the Python bridge `doc_id`
- a Qdrant point ID
- a Neo4j node ID

## Identifier Model

The contract should use these identifiers:

| Name | Scope | Owner | Meaning |
| --- | --- | --- | --- |
| `assistant_document_id` | Public API | Laravel/PostgreSQL | Stable logical file identity used by the assistant system |
| `dataset_id` | Public API | Laravel/PostgreSQL | Target dataset |
| `source_id` | Internal workflow | Laravel/Python | One ingest source/workflow identity |
| `task_id` | Internal workflow | Laravel | Pipeline task identity |
| `job_id` | Internal workflow | Laravel | Pipeline job identity |
| `bridge_document_id` | Internal indexing | Python bridge | `doc_id` used for Qdrant and Neo4j deletion/replacement |

Recommended rule:

- `assistant_document_id` is a ULID or UUID generated by Laravel and returned to the assistant.
- `bridge_document_id` is never the public primary identifier.
- Laravel may expose `bridge_document_ids` in read responses for observability, but assistant mutations should target `assistant_document_id`.

## Recommended PostgreSQL Persistence Model

### 1. `assistant_documents`

One row per logical file managed by the assistant API.

Recommended fields:

- `assistant_document_id`
- `dataset_id`
- `display_name`
- `source_type`
- `source_url`
- `source_updated_at`
- `source_checksum_sha256`
- `graph_enabled`
- `status`
- `last_error`
- `latest_source_id`
- `latest_task_id`
- `latest_job_id`
- `latest_document_version`
- `indexed_at`
- `deleted_at`
- `metadata_json`
- timestamps

### 2. `assistant_document_outputs`

One row per active or historical bridge-level indexed output derived from an assistant document.

Recommended fields:

- `assistant_document_id`
- `bridge_document_id`
- `qdrant_collection`
- `neo4j_namespace`
- `source_id`
- `task_id`
- `job_id`
- `content_hash`
- `chunk_count`
- `status`
- `active`
- `indexed_at`
- `deleted_at`
- `metadata_json`
- timestamps

### Why two tables are needed

One uploaded file can produce:

- one logical assistant document
- one or more bridge-level indexed documents
- many chunks per indexed document

The mapping table lets Laravel:

- delete all indexed outputs for one assistant document
- replace all indexed outputs on update
- report chunk totals without exposing chunk mutation APIs

### Existing PostgreSQL metadata that should be reused

The current code already writes useful indexing metadata into PostgreSQL:

- `documents.external_id` currently stores the bridge-level `document_id` written by Python
- `documents.metadata_json` currently stores fields such as:
  - `source_id`
  - `task_id`
  - `job_id`
  - `qdrant_collection`
  - `neo4j_namespace`
  - `bridge_response`
- `ingestion_sources` tracks workflow-level source state
- `ingested_pages` tracks incremental ingest metadata and per-`doc_id` chunk counts

The new assistant tables should reuse those existing records as source data rather than redefining bridge identity rules.

Recommended mapping rule:

- `assistant_documents` owns the stable public resource
- `assistant_document_outputs.bridge_document_id` should map to the same bridge `doc_id` currently stored in `documents.external_id`

## API Style

This contract should use:

- base path: `/api/assistant`
- auth: `Authorization: Bearer <sanctum-token>` for the first implementation
- request and response body naming: `snake_case`
- idempotency header: `Idempotency-Key`

Note: some existing `v1.5` endpoints use camelCase, but this assistant API should prefer one consistent machine-oriented style.

## Phase 1 API Surface

The phase 1 assistant API should expose exactly these endpoints:

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/assistant/documents` | Create a logical assistant document and start ingest |
| `POST` | `/api/assistant/documents/batch` | Create many logical assistant documents in one request using one shared dataset |
| `GET` | `/api/assistant/documents/{assistant_document_id}` | Read current status and mapped indexed outputs |
| `PUT` | `/api/assistant/documents/{assistant_document_id}` | Replace the file if it is newer, or skip if unchanged |
| `DELETE` | `/api/assistant/documents/{assistant_document_id}` | Delete all active indexed outputs from Qdrant and Neo4j and soft-delete the assistant document |

Optional later endpoint, not required for phase 1:

- `GET /api/assistant/documents`

That can be added later for listing and filtering, but it is not necessary for the assistant lifecycle MVP.

## Status Model

Assistant documents should expose one stable status field:

- `accepted`
- `processing`
- `indexed`
- `skipped_unchanged`
- `deleting`
- `deleted`
- `failed`

Recommended transition rules:

- create request accepted: `accepted`
- workflow started and still running: `processing`
- indexed outputs active and ready: `indexed`
- update skipped because incoming file is not newer: `skipped_unchanged`
- delete requested and fan-out deletion in progress: `deleting`
- indexed outputs deleted and resource soft-deleted: `deleted`
- any failed create, update, or delete workflow: `failed`

## Chunk Handling

Chunks are internal implementation details.

The assistant API must never expose chunk mutation endpoints.

Rules:

- create operates at assistant-document level
- update replaces all active indexed outputs for that assistant document
- delete removes all chunks for all active bridge documents mapped to that assistant document
- chunk counts may be returned in read responses for visibility only

If one bridge document has 83 chunks:

- the assistant still sees one logical assistant document
- delete removes all 83 chunks by bridge `doc_id`
- update recreates the full chunk set

If one uploaded file expands into 3 bridge documents:

- the assistant still sees one logical assistant document
- delete removes all chunks for all 3 bridge documents
- update replaces all 3 bridge documents as a set

## Endpoint Contracts

### 1. Create And Ingest Document

`POST /api/assistant/documents`

Content type:

- `multipart/form-data`

Request fields:

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `file` | binary | yes | Single uploaded file |
| `dataset_id` | string | yes | Target dataset |
| `source_updated_at` | RFC3339 timestamp | no | Recommended for later update comparison |
| `source_checksum_sha256` | string | no | Optional client-provided checksum |
| `graph` | boolean | no | Default `false`; if omitted, assistant ingest stays vector-only with no Neo4j graph ingest |
| `display_name` | string | no | Human label for the logical assistant document |
| `source_url` | string | no | Optional original source URL if known |
| `metadata_json` | object or JSON string | no | Assistant-owned metadata |

Behavior:

- Laravel creates one `assistant_document_id`.
- Laravel persists an `assistant_documents` row in PostgreSQL.
- Laravel starts one Temporal ingest workflow for the uploaded file.
- Laravel marks the document `accepted` or `processing`.
- When the workflow finishes, Laravel updates assistant metadata and mapped outputs.

Response:

- `202 Accepted`

Example response:

```json
{
  "success": true,
  "operation": {
    "type": "create",
    "status": "accepted"
  },
  "document": {
    "assistant_document_id": "adoc_01jz8w4g0ngv6h2m1ck2j3r9c4",
    "dataset_id": "hawki-policies",
    "status": "processing",
    "graph_enabled": true,
    "source_updated_at": "2026-07-08T13:35:00Z",
    "display_name": "transfer-guidelines.pdf"
  },
  "pipeline": {
    "task_id": "task_7e2f1d3a",
    "job_id": "ingest_4d89d2a5a73b7f95c123d4ab",
    "source_id": "source_4a3f3f3c94f2f12d56d0f7b8c6120a9c"
  }
}
```

### 1B. Create And Ingest Many Documents

`POST /api/assistant/documents/batch`

Content type:

- `multipart/form-data`

Request fields:

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `files[]` | binary[] | yes | One or more uploaded files |
| `dataset_id` | string | yes | Shared target dataset for the whole batch |
| `graph` | boolean | no | Default `false`; if omitted, all files stay vector-only with no Neo4j graph ingest |
| `metadata_json` | object or JSON string | no | Optional shared metadata applied to every created assistant document |

Behavior:

- Laravel creates one assistant document per uploaded file.
- Laravel starts one ingest workflow per uploaded file.
- Every file in the batch uses the same `dataset_id`.
- The response returns per-file success or failure details.

Response:

- `202 Accepted` when every file was accepted
- `207 Multi-Status` when some files failed

### 3. Update If Newer

`PUT /api/assistant/documents/{assistant_document_id}`

Content type:

- `multipart/form-data`

Request fields:

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `file` | binary | yes | Replacement file |
| `source_updated_at` | RFC3339 timestamp | yes unless `force=true` | Used for newest-file comparison |
| `source_checksum_sha256` | string | no | Optional checksum |
| `graph` | boolean | no | Optional override; if omitted, the stored graph setting is kept. New assistant documents default to `false` |
| `display_name` | string | no | Optional display name update |
| `source_url` | string | no | Optional source URL update |
| `metadata_json` | object or JSON string | no | Assistant-owned metadata update |
| `force` | boolean | no | Default `false`; when `true`, skip timestamp comparison and replace anyway |

Comparison rule:

- if `force=true`, replace
- else if incoming `source_updated_at` is greater than stored `source_updated_at`, replace
- else if stored timestamp is missing and checksum changed, replace
- else skip as unchanged

Replace behavior:

- Laravel looks up all active bridge outputs for the assistant document.
- Laravel deletes those bridge outputs from Qdrant and Neo4j.
- Laravel starts a new ingest workflow for the replacement file.
- Laravel keeps the same `assistant_document_id`.
- Laravel replaces the active output mapping set after the new ingest completes.

Responses:

- `202 Accepted` when replacement was queued
- `200 OK` when skipped as unchanged
- `404 Not Found`

Skipped example:

```json
{
  "success": true,
  "operation": {
    "type": "update",
    "status": "skipped_unchanged",
    "reason": "incoming source_updated_at is not newer than the stored document"
  },
  "document": {
    "assistant_document_id": "adoc_01jz8w4g0ngv6h2m1ck2j3r9c4",
    "status": "indexed"
  }
}
```

Queued replacement example:

```json
{
  "success": true,
  "operation": {
    "type": "update",
    "status": "accepted"
  },
  "document": {
    "assistant_document_id": "adoc_01jz8w4g0ngv6h2m1ck2j3r9c4",
    "status": "processing"
  },
  "pipeline": {
    "task_id": "task_9c0b53d1",
    "job_id": "ingest_c5f97eb7cf7e4a4ec91be812",
    "source_id": "source_ef0bfafbaeaaf6de29811cbec6c49229"
  }
}
```

### 4. Delete Indexed Document

`DELETE /api/assistant/documents/{assistant_document_id}`

Behavior:

- Laravel looks up all active bridge outputs for the assistant document.
- Laravel calls Python bridge `DELETE /documents/{doc_id}` once per active bridge document.
- Laravel aggregates Qdrant and Neo4j deletion results.
- Laravel marks mapped outputs inactive and soft-deletes the assistant document.

Delete semantics:

- This is a whole-document delete.
- It is not a chunk-level delete.
- It should delete from both Qdrant and Neo4j in one Laravel operation.

Response:

- `200 OK`
- `404 Not Found`

Example response:

```json
{
  "success": true,
  "operation": {
    "type": "delete",
    "status": "completed"
  },
  "document": {
    "assistant_document_id": "adoc_01jz8w4g0ngv6h2m1ck2j3r9c4",
    "status": "deleted"
  },
  "deletion": {
    "bridge_documents_deleted": 1,
    "qdrant": [
      {
        "bridge_document_id": "doc_18d86f9074d9a7a5257a2a4a2517f496c1ef111b",
        "result": {
          "status": "completed",
          "deleted": 83
        }
      }
    ],
    "neo4j": [
      {
        "bridge_document_id": "doc_18d86f9074d9a7a5257a2a4a2517f496c1ef111b",
        "relationships_deleted": 214,
        "entities_deleted": 97
      }
    ]
  }
}
```

## Contract Rules

### Rule 1: Assistant mutations target logical documents

The assistant system always acts on `assistant_document_id`.

It never mutates:

- a Qdrant point ID
- a chunk ID
- a Neo4j node ID
- a raw bridge `doc_id`

### Rule 2: Deletion fan-outs over mapped bridge outputs

Deletion and replacement must iterate over all active mapped `bridge_document_id` values for the assistant document.

This handles both:

- one bridge document with many chunks
- one uploaded file that produced many bridge documents

### Rule 3: Laravel owns orchestration, PostgreSQL owns truth

Laravel is the only assistant-facing surface.

Laravel owns:

- request validation
- assistant document identity
- newest-file comparison
- mapping between logical documents and bridge outputs
- final response contract

PostgreSQL is the system of record for assistant document state.

Qdrant and Neo4j are derived indexed stores.

### Rule 4: Timestamp comparison is document-level

Newest-file decisions are based on the logical assistant document, not individual chunks.

### Rule 5: Chunk details are reporting only

Chunk counts may appear in responses for visibility, but the assistant API does not expose chunk mutation endpoints.

## Implementation Mapping To Current `v1.5` Code

The current code already supports the execution side needed for this contract:

- create/upload can reuse Laravel upload orchestration and Temporal workflow start
- delete can reuse Python bridge `DELETE /documents/{doc_id}`
- replace can reuse Python bridge `PUT /documents/{doc_id}` or Laravel-driven delete plus reingest
- PostgreSQL already stores bridge document metadata and source workflow state

Important current behavior to reuse carefully:

- Python already stores bridge `document_id` into Laravel `documents.external_id`
- Python already writes `source_id`, task, collection, and namespace into `documents.metadata_json`
- uploaded files already bypass real crawling and are copied into the workflow raw directory

Important gap to close in implementation:

- current Laravel tables do not yet expose one stable assistant-facing logical document resource with one-to-many bridge output mapping

## Phase 1 Non-Goals

The first implementation should not try to do these things:

- chunk-level CRUD
- Neo4j-only or Qdrant-only mutation endpoints
- remote recrawl scheduling
- bulk multi-file ingest in one request
- generalized list/search UI features for assistant documents

## Recommended Next Implementation Steps

After this contract is accepted, implementation should proceed in this order:

1. Add PostgreSQL tables for `assistant_documents` and `assistant_document_outputs`.
2. Add a Laravel assistant document orchestration service.
3. Add a Laravel client wrapper for Python bridge document delete and replace.
4. Implement `POST /api/assistant/documents`.
5. Implement `GET /api/assistant/documents/{assistant_document_id}`.
6. Implement `PUT /api/assistant/documents/{assistant_document_id}` with newest-file logic.
7. Implement `DELETE /api/assistant/documents/{assistant_document_id}`.
8. Add PHPUnit feature tests.
9. Add Swagger paths and schemas.
